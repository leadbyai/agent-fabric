# Hermes backend (draft, pilot)

`hermes_bridge.py` serves AG-UI for **existing Hermes Agent profiles** on the same server, next to the
Herdr gateway (which is unchanged). It attaches to the already-running Hermes gateway using Hermes'
own supported local client:

1. `hermes_cli.gateway_runtime.discover_gateway_endpoint(profile_home)`: read-only, never spawns a gateway;
2. a one-use ticket from the gateway's private control socket (same Unix user only);
3. the loopback canonical WebSocket (`hermes-gateway-v1`).

## What is a permanent agent
A **served Hermes profile**. Its stable identity is `(install_id, profile_id)`: the install id comes from
`profiles.list`, and the profile id is the profile home. `instance_id` changes per gateway run and is only
runtime state. Cron executions, subagents (`delegate_task` children) and individual conversations are
never listed as agents. Only profiles named in `HERMES_PROFILES` are exposed.

## Routes
| Route | Auth | Purpose |
| --- | --- | --- |
| `GET /health` | none | liveness |
| `GET /agents` | bearer | allowed, served profiles with stable identity and display name |
| `POST /profiles/<name>/ag-ui` | bearer | one AG-UI run |
| `GET /requests/<id>` | bearer | ledger state of a run |

## Authentication
The bridge never stores a bearer token; it keeps only SHA-256 hashes and compares in constant time.
- **Per-profile tokens (recommended):** `--profile-token-sha256 <name>=<sha256>` once per listed profile.
  Each token reaches only its own profile: `GET /agents` lists only that profile, `POST` to another
  profile's route is 404 without contacting Hermes, and `GET /requests/<id>` hides other profiles' runs.
  A hash may be used for one profile only, and every listed profile needs one. The installer writes
  `profile-tokens.sha256` (mode 0600) and removes any bridge-wide token, so no token reaches every profile.
- **Bridge-wide token (older setup):** `--token-sha256 <sha256>` or `--token-file`; one token reaches
  every listed profile.

The token itself is generated by the client (for example inside OpenBot, stored in its encrypted vault),
and only its hash is handed to the installer. Re-running the installer replaces the hash file, so pass
every profile's hash each time.

## Model changes without a gateway restart
New sessions are created with `follow_profile_config=true` when the gateway advertises that
`session.create` parameter. Such a session re-reads the profile's current model and provider sections
each turn (Hermes' own "Bot Chat" behaviour), so a profile model change applies to OpenBot without
restarting the Hermes gateway. Existing thread mappings keep the settings they were created with.
Set `HERMES_FOLLOW_PROFILE_CONFIG=0` to opt out.

## Sessions and safety
- Each OpenBot thread gets **its own new Hermes session**, with `session.create` and source `gui`. The
  thread → session map lives in the private ledger, and later runs resume that session. The bridge never
  attaches to TUI, messaging, cron or subagent sessions it did not create.
- **Existing-session binding** (off by default): an operator can bind a thread to an existing native
  session id (`origin = bound`). It is resumed only with `HERMES_ALLOW_NATIVE_ATTACH=1`. The Hermes REST
  sessions API is never used to claim sessions.
- **Only sessions it created:** Hermes resolves a session title as an identity, so titles carry a hash of
  profile and thread. When the gateway supports it, `session.create` also sends a per-thread `client`
  label, and the result must echo it in `info.launch_request`; a result whose `info.source` is not `gui`,
  whose label differs, or whose session another thread already owns is refused before any prompt.
- **Idempotency:** `prompt.submit` carries `input_id = H(profile, thread, run)`, and the ledger replays a
  finished run or refuses an in-doubt one. A run is never resent.
- **Approvals:** surfaced as a CUSTOM `agent-fabric.approval` event plus a text notice, then answered
  with the offered deny choice. `unattended` is never set, because it would auto-approve.
  Clarify prompts are answered as skipped.
- **Tool activity:** reported as CUSTOM `agent-fabric.tool` events, not AG-UI `TOOL_CALL_*`. OpenBot
  would treat those as tools for it to run.
- **Binding:** loopback or the host's Tailscale (100.64.0.0/10) address only.

### Screenshots on a dedicated existing-session bridge

Run the bridge with `HERMES_HOME` pointing to the target profile's home, a single
`HERMES_PROFILES` route, `HERMES_ALLOW_NATIVE_ATTACH=1`, and exact
`HERMES_BOUND_THREAD_ID` and `HERMES_BOUND_SESSION_ID` values. Setting
`HERMES_BRIDGE_MEDIA_ROOT` to an existing private directory owned by the bridge user
enables PNG, JPEG and WebP uploads and replies on that route. Other threads are refused.

OpenBot sends inline image data and the bridge submits it through Hermes' native
attachment admission. The bridge creates a private reply directory for each turn.
Images saved there are embedded in the authenticated reply with the existing screenshot
size and file checks. Identical retries replay the stored reply and changed input under
the same run ID is refused. Deployments without a media directory retain text-only behavior.

### Isolated shared profile (`HERMES_ISOLATED_PROFILE=1`)

For people an owner shares a Bot with, run a **second** bridge in front of a **separate** Hermes profile, never the
owner's. With `HERMES_ISOLATED_PROFILE=1` the bridge:

- serves exactly one route (`HERMES_PROFILES` has one name) backed by its own explicit `HERMES_HOME`, which must
  not be the default Hermes home;
- refuses `HERMES_ALLOW_NATIVE_ATTACH`, `HERMES_BOUND_THREAD_ID`/`HERMES_BOUND_SESSION_ID` and
  `HERMES_BRIDGE_MEDIA_ROOT`, so every thread gets its own new `gui` session, a native binding is never resumed,
  and attachments are refused;
- refuses to start, and re-checks before **every run** (503 when it fails), unless the profile's **effective**
  Hermes config (defaults included) reads cleanly (a fallback or last-known-good config is refused) and has:
  - no messaging platform enabled and no platform credential in `config.yaml`, the profile `.env` or the
    environment (checked by name only);
  - `memory.memory_enabled: false`, `memory.user_profile_enabled: false` and no `memory.provider`;
  - `platform_toolsets` `cli`, `tui` and `gui` set to `[]` and every other platform empty;
  - Hermes' client-surface toolsets (`project`, `desktop_ui`, `catalog`) in `agent.disabled_toolsets`;
  - no `mcp_servers`, no `plugins.enabled`, and `agent.coding_context` other than `focus`;
- creates every session with an explicit `toolsets: []` and the per-thread `client` label, and never with
  `follow_profile_config`. The **gateway** enforces the empty pick, and it also skips the GUI surface fold-in
  that otherwise adds client-surface toolsets to GUI sessions. A gateway that does not advertise both
  parameters is refused.

Give the shared bridge its **own bearer**: the owner's pinned bridge only accepts the owner's.

This is **capability** isolation. It does not stop a process from reading files its Unix user can read. Run
the isolated profile as a different OS user, or in a disposable container with nothing of the owner's
mounted and no inherited credentials, with only the egress its model provider needs.

## Install (as the profiles' Unix user; additive user service)
```bash
bash install-hermes.sh --source-dir <reviewed checkout> --profiles <a>,<b> --bind <tailscale-ip> --port 8767 \
  --profile-token-sha256 <a>=<sha256> --profile-token-sha256 <b>=<sha256>
bash install-hermes.sh --uninstall   # rollback
```
`install.sh --backend hermes|both` delegates here. `--backend herdr` (the default) is the unchanged Herdr install.
