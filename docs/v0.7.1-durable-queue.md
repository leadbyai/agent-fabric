# Agent Fabric v0.7.1: durable queue state and screenshot-safe history

Status: **draft / release candidate `v0.7.1-rc1`; offline-tested only, not deployed.**
Builds on v0.7.0-rc3 (PR #7, `cccf263`). v0.7.0 is already tagged (`44df55a`), so the next final release is **v0.7.1**, not another v0.7.0-rcN.

## Problems fixed

1. **Queued messages vanished on a gateway restart.** The per-pane FIFO wait queue lived only in memory, and a ledger row was written only at submit time. A message waiting behind a busy agent when the gateway restarted (installer run, crash, reboot) left no trace. The user saw a dropped stream, and nothing recorded what had happened.
2. **Screenshot-heavy chats eventually could not be continued.** OpenBot resends the whole conversation on every run. Inline `data:image` screenshots from v0.7.0 build up in assistant messages, about 2.7 MiB of base64 per 2 MiB image. A few replies with screenshots push every later turn in that chat over the 64 MiB body limit, and each one is refused with 413.

## What changes

### Ledger states (`request_ledger.py`)

| State | Meaning | Resend allowed? |
| --- | --- | --- |
| `queued` | **new.** Accepted and waiting for the agent; prompt not sent | — |
| `submitted` | prompt being sent / agent working | no |
| `finished` | reply stored, replayed on retry | replay only |
| `uncertain` | failure after submit; the prompt may have been sent | no |
| `failed` | **new.** Definitely never sent; `reason` says why | yes, same run id may be queued again |

- The request is written as `queued` as soon as it is accepted, before any waiting, and the stream gets a `agent-fabric.request {state: queued}` event. Just before the Herdr prompt is sent, the same row moves to `submitted`. Only the owner can do this (the marker must match).
- These events mark a request `failed` with a reason, and never touch `submitted` rows:
  - the wait expires;
  - the agent changes, is blocked, or the gateway hits capacity;
  - the client disconnects while queued;
  - the gateway shuts down.
- **Startup:** every row still `queued` is marked `failed` (`gateway_restarted_before_submit`), because no waiter survives a restart. The startup log reports how many.
- **SIGTERM:** the gateway stops accepting runs (`503 gateway_restarting`). Queued waiters get `RUN_ERROR` "Gateway is restarting; this queued request was not submitted. Please resend it." and are recorded as `failed`. The gateway then stops; the grace period is at most 5 s.
- **Not changed:** requests already submitted behave exactly as in v0.7.0. They stay `submitted`, the ledger blocks any resend, and they are listed as unresolved.
- `/requests/<id>` now also returns `reason`, `queued_at` and `updated_at`. `/attention` adds `queued_requests` and `recent_failed_requests` (24 h).
- `failed` rows are trimmed after 7 days, like `finished`. `queued`, `submitted` and `uncertain` rows are never trimmed.
- Queued rows hold only fingerprints, never prompt text, which is the same privacy design as before. So a failed request **cannot be resent automatically**; the person resends it. Deliberate choice: an automatic resend after a restart risks a duplicate when the person has already resent it.

### Schema migration
- On the first start of v0.7.1, the `requests` table is rebuilt in one transaction to widen the state CHECK and add `queued_at` and `reason`. Row counts are verified, and on any error the old table is kept.
- **Rollback-safe:** v0.7.0 code opens a migrated ledger normally (tested). It treats a `queued` or `failed` row with the same key as "already submitted" and refuses, failing closed.
- The installer now takes an online sqlite backup, `requests.sqlite3.bak.<stamp>`, before restarting.

### History data-URI stripping (`bridge.py`)
- The request body is streamed through `DataUriStripper` before JSON parsing. Any `data:image/<type>;base64,` run of at least 4 KiB is replaced with `OPENBOT_OMITTED`. Short runs and bare base64 (the latest message's real AG-UI attachments) are untouched. The filter handles JSON `\/` escapes and every chunk boundary.
- The wire limit is now 512 MiB, streamed. The **stripped** body must still be ≤ 64 MiB (413 otherwise), so memory stays bounded as before.
- Only the latest user turn was ever used, so behaviour is unchanged apart from no longer hitting 413 on long screenshot chats. OpenBot's stored conversation is unchanged.

## Tests
`python3 -m unittest discover -s tests -p 'test_bridge.py'`: **46 pass**, comprising the 32 from rc3 plus 14 new ones:
- queued row visible during the wait, then submitted, then finished;
- expired wait recorded as `failed`, and a retry with the same run is delivered;
- restart while B waits behind A: A stays `submitted` and B becomes `failed (gateway_restarted_before_submit)`;
- SIGTERM: the waiter gets RUN_ERROR, the row is `failed`, a new POST gets 503, and no prompt is sent;
- client disconnect while queued is recorded as `failed`;
- FIFO A/B both end `finished`;
- a history carrying a 3 MiB screenshot passes under a 512 KiB limit, the real upload in the latest turn arrives intact, and no base64 appears in the prompt;
- an oversize latest message still returns 413;
- ledger migration from the v0.7.0 schema keeps its rows and is idempotent;
- v0.7.0 code on a migrated ledger fails closed;
- `reserve` promotes only its own queued row, and `fail()` never downgrades `submitted`;
- stripper at chunk sizes 1, 2, 3, 7, 13, 64 and 1000, with JSON `\/` escapes, short runs kept, bare base64 untouched.

## Canary (after approval only)
1. Back up as for v0.7.0. The installer now also snapshots the ledger.
2. Confirm 0 unresolved ledger rows and no open connections to :8766.
3. Install on the gateway host with the **current** options. Confirm `Ledger:` and `Bridge ready` in the journal, `/health` 0.7.1, and that the migrated ledger row count equals the count before.
4. Round trip to a scratch pane. Then a FIFO A/B to one scratch agent. Then restart the gateway while B is queued: B should show RUN_ERROR and be `failed` in `/attention`, never silently lost.
5. Send a chat with three agent screenshots, then a fourth turn. It should get no 413, and the journal should show `omitted N inline data-URI image(s)`.
6. Rollback: the installer `.bak` files. The migrated ledger works with v0.7.0 code, and the snapshot exists anyway.
